Generate once

Why KubeGenX exists

Generate once. Serve any timeline.

KubeGenX builds the usage history Thanos would hold for a real Kubernetes cluster, then lets you place that history on any calendar. The samples are created a single time. A new end time becomes a new Thanos, or a Kruize feed, over the same files.

  • Real series. Container CPU and memory, kube-state-metrics, GPU metrics, and the recorded rates Kruize and OpenShift expect.
  • Built a single time. The usage pattern belongs to the workload. Which week it appears on is chosen when you serve. A full-size run is on the order of a hundred billion samples.
  • Served on demand. Ask for an end time. Thanos gets blocks for that window. Kruize gets JSON pages stamped with that window, built as each page is requested.

Thanos export

Blocks for this window

The controller writes TSDB blocks with these timestamps and starts a store gateway, querier and route. Point Kruize local monitoring, or any PromQL client, at that Thanos. Another end time is another export, with its own blocks.

Kruize session

Pages, stamped as they are served

Experiment and result JSON are built when requested, with this offset. The experiment name stays dataset|namespace|kind|workload. Give each timeline its own Kruize so the histories stay apart.

5a · Thanos

Materialize a timeline

Pick an end time. The controller reads the parquet, stamps the offset, writes 24-hour TSDB blocks sharded by series, and adds the Thanos metadata. A private store and querier serve that directory on a route.

5b · Kruize remote

Serve a timeline live

Open a session with an end time. The offset is fixed for the life of the session. Experiment pages come from the plan. Each results page is one 6-hour chunk, aggregated when that page is requested. Several sessions can be open on different clocks.

Design choices

Why it is built this way

Short reasons for the pieces that make “generate once, serve many clocks” practical at cluster scale.

Format

Parquet holds the samples

Labels live in the plan. Sample files hold an id, a step index and integers, packed as deltas and compressed to a few bytes per sample. One file is a workload batch for one 6-hour chunk, so a page or a block window opens only the files it needs.

Columnar files can be pruned by workload and time, and both the block writer and DuckDB read them in place.

Scale

Generation is a queue of chunks

Rust workers lease a batch from the controller over gRPC and use every core. They keep nothing locally. The output path is computed from the batch id, so a completed file is simply the file at that path. Worker jobs leave when the dataset is done.

A hundred billion samples only works as parallel, restartable work. A lost pod costs the in-flight batches, redone identically.

Time

A step index, then an offset

Samples remember how many 15-second steps they sit from the dataset epoch. Serving floors the chosen end to 15 minutes and sets the offset against the original end. Exports and sessions remember the offset they were opened with, so a long paginated read never slides.

Moving a timeline changes a parameter. The expensive files stay where they were written.

Shape

Rates and ownership are derived

kube-state-metrics is stored as intervals and expanded to a 30-second series while serving. The recorded CPU series — sum_irate, sum_rate5m and sum_rate — are computed from the counter in that same pass. Memory and GPU gauges are generated with the container samples.

Written as raw samples, the mapping series alone would outweigh everything else. The dataset keeps the signal that actually varies.

State

SQLite for churn, DuckDB for scans

Leases, retries, progress and sessions are small transactional rows in SQLite. DuckDB scans the parquet in place for Kruize pages, storage totals and expected values. Templates, datasets and exports are ConfigMaps in kube-gen-x, so install stays inside one namespace.

Tiny writes and columnar reads are different jobs. Each has an embedded engine, and the cluster’s own monitoring is left alone.

Serving

One Thanos per timeline

PromQL needs real blocks. The controller writes them directly from parquet, in 24-hour windows split by series so memory stays bounded, and records a Thanos section in meta.json. That export mounts its block directory as a filesystem bucket and runs its own store and querier.

Each shift is a Thanos you can query today. A second shift gets its own blocks, so two clocks never share a history.

What a query finds

The series Thanos ends up serving

Enough for Kruize metadata, Kruize recommendations and the OpenShift recording rules to behave as they would on a live cluster.

  • Container CPU and memorycAdvisor counters and gauges, every 15 seconds, with the usual kubelet labels.
  • kube-state-metricsPod, owner, replica-set and container mapping series, expanded from intervals at 30 seconds so the joins resolve.
  • Recorded CPU ratessum_irate, sum_rate5m and sum_rate, computed from the counter while the blocks or the result page are produced.
  • GPU metricsDCGM-style series for the workloads that were planned with a GPU, on the same step as the container data.

Times in the demo are UTC midnight. A real export or session floors the end to 15 minutes and keeps that offset until you close it.
